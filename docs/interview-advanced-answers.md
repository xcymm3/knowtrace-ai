# 全栈偏前端面试进阶题标准答案

这份题库补充 React、TypeScript、接口、数据库、数据结构、异步和项目复盘问题。每个答案按一两分钟可口述的长度组织。涉及“你负责什么”的题目必须按真实经历替换方括号内容，不能把没有做过的模块说成自己独立完成。

## 一、React 与前端工程

## 1. `useState`、`useEffect`、`useMemo`、`useCallback` 分别适合什么场景？常见误用是什么？

`useState` 用于组件自身会变化、且变化后需要刷新界面的数据，例如输入框值、请求 loading 状态、当前工作区、文档列表和流式回答文本。更新 state 时要通过 setter，而不是直接修改变量。

`useEffect` 用于和组件外部系统同步，例如请求接口、订阅事件、计时器或读取浏览器 API。比如 `workspaceId` 改变时加载对应文档。它不适合单纯从现有 state 计算一个值；这种值应该在渲染时直接计算，避免多维护一份可能不同步的 state。

`useMemo` 缓存一次计算结果，适合确实昂贵的计算，或需要稳定对象引用的场景，例如对大量文档做筛选、排序后的派生列表。`useCallback` 缓存函数引用，常用于把回调传给经过 `React.memo` 优化的子组件，或作为其他 Hook 的依赖。

常见误用是把所有值和函数都套上 `useMemo`、`useCallback`。它们本身也有维护依赖和比较成本，简单计算、普通点击函数不需要优化。另一个误用是 Effect 依赖漏写，导致闭包中拿到旧值；或者把每次渲染新建的对象放进依赖，造成重复请求甚至循环。

## 2. React 组件如何拆分？状态放在哪里？

组件拆分以职责和复用边界为主。一个组件同时处理页面布局、请求、复杂表单、文档列表和弹窗时，就应该拆分。比如工作区页面可拆为 `WorkspaceHeader`、`DocumentUploader`、`DocumentList`、`ChatPanel`、`CitationPanel`。可复用的展示组件只接收 props；请求和页面编排留在容器或页面组件。

状态应放在最靠近使用它、但能被所有需要它的组件共享的位置。只被一个输入框使用的 state 放在输入组件；文档列表和上传结果都需要的数据放在它们共同的父组件；跨多个页面或层级使用的登录态、主题等可以放在 Context 或状态库。不要为了方便把所有 state 都放到全局，也不要让多个组件各存一份同样的数据。

## 3. 父子组件和跨层组件如何通信？

父组件通过 props 向子组件传数据；子组件通过回调 props 把事件和结果通知父组件。例如父组件传 `onDelete(documentId)`，子组件点击删除后调用它。这样数据流方向清楚，便于定位更新来源。

跨层但范围有限的共享数据可以通过 React Context，例如当前认证用户或当前工作区。状态很多、更新频繁、跨页面复杂时再考虑 Zustand、Redux 等状态库。无论用哪种方式，都应避免把后端数据复制到多个状态位置；以一个可信数据源为准。

## 4. 什么是受控组件？为什么表单要校验？

受控组件是指表单值由 React state 控制。输入框用 `value` 显示 state，用 `onChange` 更新 state。这样可以统一实现即时校验、提交时校验、禁用按钮和回填默认值。

前端校验主要改善体验，例如文件类型不支持、问题为空、名称超长时及时提示，减少无效请求。提交时仍要由后端校验，因为前端代码可被绕过或篡改。校验信息应该贴近字段、表述清楚；提交失败时要保留用户输入，避免用户重填。

## 5. 列表渲染中的 `key` 为什么重要？

React 用 key 判断列表项在前后两次渲染中是否是同一个元素，从而正确复用、移动或销毁对应 DOM 和组件状态。文档列表应使用后端返回的稳定文档 ID。若使用数组下标作为会插入、删除、排序列表的 key，某一行的输入状态、展开状态可能错位到另一条数据。

## 6. 页面卡顿时如何排查？

我会先复现卡顿并用 React DevTools Profiler、浏览器 Performance 和 Network 面板定位。重点检查四类问题：

1. **重复渲染**：看哪些组件渲染次数异常，确认是否因为父组件 state 变化、props 引用不稳定或 Context 范围过大引起。确认后才考虑拆组件、稳定 props、使用 memo。
2. **长列表**：数千条列表不能一次完整渲染，可分页、虚拟列表或按需加载。
3. **大计算**：排序、筛选、复杂转换是否在每次渲染执行；可以缓存计算、放到 Worker，或调整交互时机。
4. **请求和资源**：Network 中看是否重复请求、接口过慢、图片/脚本过大。可取消过期请求、做防抖、压缩资源、懒加载和缓存。

不能只靠感觉加 `useMemo`。先测量瓶颈，再针对性优化，并对比优化前后的性能数据。

## 7. 防抖和节流的区别与实际应用是什么？

防抖（debounce）是连续触发后，等停止一段时间才执行一次。适合搜索框输入、窗口尺寸变化后重新请求等场景，目的是避免每次输入都请求。

节流（throttle）是在一段时间内最多执行一次。适合滚动、鼠标移动、拖拽等持续高频事件，目的是保证持续过程中仍按固定频率更新。

例如知识库搜索框可以在用户停止输入 300 毫秒后发请求；滚动时更新浮动工具栏位置可以每 100 毫秒最多执行一次。实现时还要在组件卸载时取消延迟任务，避免已离开页面还执行更新。

## 8. 常用工程实践有哪些？

我会使用 ESLint 发现未使用变量、错误 Hook 用法和潜在代码问题；使用 Prettier 统一格式，减少无意义的格式争论。请求层会统一封装 base URL、JSON 解析、token 注入、错误转换和超时/取消处理，业务组件只调用语义化方法，例如 `getDocuments`、`deleteDocument`。

错误处理上，网络错误、参数错误、权限失效和服务端异常要给用户不同且可行动的提示；同时保留必要日志。权限路由只用于界面体验，例如未登录跳转登录页；真正的权限校验必须在后端。组件复用上优先抽取有稳定职责和统一交互的组件，例如按钮、对话框、空状态、分页和文档状态标签，而不是过早做过度抽象。

## 二、TypeScript 与 JavaScript 异步

## 9. `interface` 和 `type` 有什么区别，如何选择？

两者都能描述对象结构。`interface` 很适合定义对象、类契约，并支持声明合并和 `extends`；`type` 更灵活，除了对象外还能表达联合类型、交叉类型、元组和基础类型别名。

我在业务中一般用 `interface` 描述稳定的数据对象或组件 props，用 `type` 描述状态联合、工具类型和组合类型，例如 `type TaskStatus = 'queued' | 'running' | 'failed'`。关键是团队统一，而不是纠结谁绝对更好。

## 10. 什么是泛型？

泛型是把类型作为参数传入，让一段通用逻辑在复用时仍保留具体类型。例如请求函数 `requestJson<T>` 的返回值是 `Promise<T>`，调用 `requestJson<Document[]>` 后，编辑器知道结果是文档数组。泛型避免了把返回值写成 `any`，保留类型提示和检查能力。

## 11. 什么是联合类型和可选属性？

联合类型表示值可以是几个明确类型或值之一。例如处理状态可以是 `queued | running | succeeded | failed`，这样非法状态会在编译时暴露。可选属性用 `?` 表示它可能不存在，例如失败前没有 `errorMessage`。读取可选属性时要处理 `undefined`，不能假定它一定有值。

## 12. 如何定义接口返回值类型？还需要运行时校验吗？

前端应为接口请求和响应定义类型，例如 `DocumentListResponse`、`CreateDocumentResponse`，让字段命名和使用方式清晰。后端则用 Pydantic 等工具定义并校验请求模型与响应模型。

仍需要运行时校验。TypeScript 类型在编译后不会存在，网络返回、旧客户端和第三方服务都可能给出意外数据。后端必须做严格参数校验；前端至少应对关键字段、空值和异常响应做保护，不能把 `as SomeType` 当成真实校验。

## 13. Promise、async/await 是什么关系？

Promise 表示一个未来才会完成或失败的异步结果，状态可以是 pending、fulfilled 或 rejected。`async/await` 是基于 Promise 的更易读写法：`async` 函数总会返回 Promise，`await` 会等待一个 Promise 完成并拿到结果。它不会阻塞整个 JavaScript 线程，只是暂停当前 async 函数的后续逻辑。

异常可用 `try/catch/finally` 处理：`try` 执行请求，`catch` 转换错误并提示用户，`finally` 收尾，例如关闭 loading。不要只 catch 后吞掉错误，否则排查会困难。

## 14. 如何处理并发请求？

相互独立的请求可以用 `Promise.all` 并发执行，缩短总等待时间；其中一个失败就希望整体失败时适合使用它。需要了解每项最终结果、允许部分失败时可用 `Promise.allSettled`。有先后依赖的请求必须顺序 `await`，例如先创建文档才能开始处理该文档。

还要防止竞态：用户很快切换工作区时，旧请求可能后返回并覆盖新数据。可以使用 `AbortController` 取消旧 fetch，或在返回时确认请求仍属于当前 workspaceId。

## 三、HTTP、接口与认证

## 15. GET、POST、PUT/PATCH、DELETE 的常见用法是什么？

GET 用于读取资源，不应产生业务副作用，例如获取文档列表。POST 用于创建资源或触发无法用简单资源更新描述的动作，例如创建工作区、上传文件、开始问答。PUT 通常表示用完整资源替换原资源；PATCH 表示部分字段更新，例如只改工作区名称。DELETE 表示删除资源，例如删除文档。

实际项目还要考虑幂等性。GET、PUT、DELETE 设计上通常应多次执行结果一致；POST 不一定幂等。对于可能重试的创建操作，可以加幂等键或唯一约束，避免重复创建。

## 16. RESTful 接口如何设计？

路径应该围绕资源名而不是动词，例如 `/workspaces/{workspaceId}/documents` 表示某工作区下的文档集合，`/documents/{documentId}` 表示单个文档。读取筛选、排序、分页用查询参数，例如 `?page=1&pageSize=20&status=succeeded`；创建和复杂数据放请求体。

响应结构需要稳定，成功时返回前端所需的数据，失败时返回机器可读的错误码和用户可读的错误信息。状态码也要符合语义，例如创建用 201、参数不合法用 400 或 422、未认证用 401、无权限用 403、资源不存在用 404、后端未预期异常用 500。

## 17. 统一响应结构应该如何理解？

统一响应结构的目的，是让前端能一致地处理成功、业务错误和系统错误。例如成功可以是 `{ data: ..., requestId: '...' }`，错误可以是 `{ error: { code: 'DOCUMENT_NOT_FOUND', message: '文档不存在' }, requestId: '...' }`。文件下载或 SSE 流这类场景不一定适合强行包一层 JSON，应按协议特点处理。

无论结构怎样，接口契约要写清字段含义，错误码要稳定。后端日志也应记录 requestId，方便从前端报错定位到对应服务端请求。

## 18. 登录鉴权的基本思路是什么？JWT 放在哪里、如何携带？

用户登录后，Supabase Auth 签发 access token，通常是 JWT。前端每次调用受保护 API 时，在请求头携带 `Authorization: Bearer <token>`。后端验证 token 的签名、有效期和必要声明，得到当前用户 ID，再根据用户 ID 检查目标工作区、文档是否属于该用户。

token 的存放要结合架构权衡。较安全的网页方案常使用 `HttpOnly`、`Secure`、`SameSite` Cookie，脚本无法直接读到它，能降低 XSS 窃取风险，但要配合 CSRF 防护。若 token 放在 localStorage，实现方便但一旦发生 XSS 更容易被读走。无论存哪里，都不能把服务端高权限密钥放到浏览器。

## 19. 为什么不能只靠前端校验参数和权限？

浏览器由用户控制，用户可以修改页面 JavaScript、直接用 Postman/curl 调用接口，或者伪造请求。因此前端校验只能改善体验，不能建立安全边界。后端必须校验参数类型、长度、范围、文件类型、必填字段和业务状态；还要从 token 得到真实用户身份并检查资源归属。

例如前端即使没有“删除其他人文档”的按钮，攻击者仍能构造 DELETE 请求。后端如果没校验 documentId 对应的 workspace 和 owner，数据就会泄露或被删除。

## 20. 400、401、500 分别怎么排查？

400 或 422 一般说明请求不符合接口要求。我会先看 Network 里的 URL、方法、Content-Type、请求体和后端返回的字段错误，再对照接口文档；常见原因是必填字段缺失、类型不对、分页参数非法或 multipart 上传方式错误。

401 一般检查是否未携带 token、token 过期、token 格式不对或服务端验证配置不一致。500 表示服务端出现未处理异常，前端应展示友好提示和 requestId，后端要看异常栈、关联日志、数据库或第三方服务状态。不能把 500 一律归因于“前端传错了”。

## 21. 前后端联调常见的细节问题有哪些？

常见问题包括字段大小写不同、前端发 JSON 而后端期待表单、空字符串和 `null` 的语义没有约定、日期时区和格式不同、枚举值不一致、分页从 0 还是 1 开始不一致、返回总数和下一页规则不一致，以及开发环境的跨域限制。

处理方式是先写清 API 契约，再用 Swagger/OpenAPI 或接口工具验证后端，前端按契约接入。发生问题时提供请求路径、方法、状态码、请求响应摘要和 requestId，而不是只说“接口有问题”。

## 四、SQL 与 PostgreSQL

## 22. SQL 中 SELECT、WHERE、JOIN、GROUP BY、聚合、排序和分页如何使用？

`SELECT` 选择要返回的列，`WHERE` 过滤行，`JOIN` 按关联字段组合多张表，`GROUP BY` 分组，`COUNT`、`SUM`、`AVG` 等聚合函数计算每组统计值，`ORDER BY` 排序，`LIMIT/OFFSET` 实现基础分页。

例如查询某工作区每种文档处理状态的数量，可以先 `WHERE workspace_id = $1`，再按 `task_status GROUP BY`，并用 `COUNT(*)` 统计。查询文档列表时按 `created_at DESC` 排序，再用 `LIMIT` 和 `OFFSET` 返回一页数据。数据量很大、翻到深页时，OFFSET 可能变慢，可使用基于 `created_at` 和 ID 的游标分页。

## 23. PostgreSQL 表设计时要考虑什么？

先从业务实体和关系出发。工作区、文档、文本 chunk、会话、消息、引用和处理任务分别有自己的表；表使用稳定主键，相关表用外键表达关系。字段类型要符合数据含义，例如时间用时间类型，状态用受控枚举或约束，不把所有内容都塞进一个 JSON 字段。

还要考虑非空约束、唯一约束、删除策略、查询方式和权限边界。比如 documents 需要 workspaceId 和文件名，chunks 需要 documentId 和文本位置，回答引用需要 answerId 与 chunkId 的关联表。删除文档时也要同步清理 Storage 对象、chunk、向量、引用和任务。

## 24. 主键、外键、索引和事务分别是什么？

主键唯一标识一行；外键表示表之间的引用关系，维护数据一致性；索引是帮助数据库更快定位数据的数据结构；事务把多个数据库操作作为一个整体，要么全部提交，要么出错回滚。

例如文档 ID 是主键，文档的 workspaceId 是指向工作区的外键。按 workspaceId 查询文档很频繁时可建立索引。创建文档及其任务记录可放入事务，避免只写入一半业务数据。

## 25. 索引为什么加速查询，又为什么不能无脑建？

没有索引时，数据库可能需要扫描整张表逐行判断；索引通常用 B-tree 等结构把列值组织起来，能更快缩小候选记录范围，所以对高频过滤、排序、关联的字段有帮助。

但索引占磁盘和内存，每次 INSERT、UPDATE、DELETE 都要维护索引，也会降低写入速度。低选择性字段，例如只有“是/否”的列，单独索引未必有收益。是否建索引要结合真实查询、数据量和执行计划判断，而不是给每一列都加。

## 26. PostgreSQL 事务在项目中怎样使用？

事务用于保证相关数据库写入的一致性。例如创建文档记录和任务记录时，二者应同时成功或回滚。事务具备原子性、一致性、隔离性和持久性。

但上传 Storage 文件、投递 Redis 任务是跨服务操作，不能被一个 PostgreSQL 事务完全包住。对此要考虑部分成功：例如文件上传成功但建库失败要清理文件；任务投递失败要标记失败或支持重新投递。必要时通过状态机、重试、幂等键和补偿任务保证最终一致性。

## 五、数据结构与算法思维

## 27. 数组、对象/哈希表、栈、队列、链表、树分别适合什么用途？

数组适合有序列表和按下标访问，例如前端文档列表、消息列表；对象或 Map 适合按唯一 key 快速查找，例如按 documentId 找文档。栈是后进先出，常见于函数调用和撤销操作；队列是先进先出，适合任务排队。

链表擅长在已知节点位置插入删除，但按位置访问慢，JavaScript 业务代码通常优先数组。树适合层级关系，例如文件目录和组件层级。选择依据是读取、插入、删除、去重和排序哪一种操作最频繁。

## 28. 常见时间复杂度如何理解？

遍历 n 个元素通常是 O(n)；通过哈希表/Map 按 key 查找平均是 O(1)；高效排序通常是 O(n log n)；两层遍历比较可能是 O(n²)。复杂度描述数据量增大时的增长趋势。

例如少量文档用 `array.find` 是清晰且足够的；如果需要反复按 ID 查找成千上万条数据，可以预处理成 Map。复杂度只是判断工具，优化前要考虑真实数据规模和可读性。

## 29. 双指针、滑动窗口、哈希去重、递归/迭代、二分查找是什么思路？

双指针在有序数组或区间问题中用两个位置向中间或同向移动，常把双重循环降为线性遍历。滑动窗口维护一个连续区间，适合“最长无重复子串”“固定长度区间统计”这类问题。

哈希去重用 Set 或 Map 记录已经见过的值，快速判断重复。递归通过函数调用自身解决可拆成相似子问题的场景，例如树遍历；迭代通过循环和显式数据结构完成，通常避免过深递归栈。二分查找只适合有序且可随机访问的数据，每次排除一半范围，复杂度是 O(log n)。

## 六、项目、质量与复盘

## 30. 你负责的模块具体是什么，代码中哪些部分是你独立完成的？

**这题必须按真实经历回答。**可以使用这个结构：

> 我主要负责 [模块名称]，范围是从 [用户操作或需求] 到 [交付结果]。具体完成了 [页面/组件]、[接口调用或后端接口]、[异常处理/测试]。例如在 KnowTrace AI 中，我负责 [工作区文档上传与任务状态展示 / 对话界面与 SSE 流式输出 / 某个后端解析流程]，实现了 [具体文件或功能]，并和 [同事或后端] 对齐了 [接口、状态和错误码]。我不负责的 [模块] 由 [谁/团队] 完成，但我了解它通过 [接口或数据流] 与我的模块协作。

如果项目是个人项目，可以如实说“核心开发由我完成”，再分清哪些是自己设计实现、哪些是基于 Supabase、FastAPI、LangChain 等现成能力集成，不夸大为从零实现底层服务。

## 31. 为什么选这个技术方案？有没有其他方案？

可以回答：

> 前端选择 Next.js、React 和 TypeScript，是因为 React 组件生态成熟，Next.js 提供路由和工程能力，TypeScript 能约束接口数据。核心业务后端选择 FastAPI，是因为 Python 对文档解析、向量化和异步任务生态支持好。数据用 Supabase 的 PostgreSQL、Auth 和 Storage，可以减少基础设施搭建成本；pgvector 让业务数据和向量检索放在同一个数据库中。耗时任务用 Redis 和 ARQ Worker，避免阻塞上传接口。

其他方案当然存在：可以全部用 Next.js Route Handler，也可以用 Node/NestJS 后端；向量库可以独立使用 Milvus、Qdrant 等；任务队列也可以用 Celery。当前选择更适合项目规模和开发效率。项目数据量、检索吞吐和团队规模进一步增长时，再评估专用向量库、独立搜索系统或更成熟的任务平台。

## 32. 遇到过什么线上问题，怎么定位和修复？

如果你没有真实线上事故，不要编造。可以诚实回答一次开发或测试环境中的问题：

> 我遇到过上传后前端一直显示处理中。我的排查顺序是先看浏览器 Network，确认上传接口返回的是 `queued`，再查 PostgreSQL 中任务状态和 Worker 日志，最后确认 Redis 中任务是否被消费。原因是 [按真实情况填写，例如 Worker 没启动/环境变量配置错误/文件解析异常没有把失败状态写回]。修复后，我补充了 [错误日志、任务超时、失败状态展示、重试入口或健康检查]，并用上传成功、解析失败和重试成功三条路径验证。

这个答案的重点是说明可复现现象、排查证据、根因、修复与防再发措施，而不是事故大小。

## 33. 如何保证质量？有没有单测、接口测试、代码评审、灰度或监控？

可以回答：

> 我会分层保证质量。开发阶段使用 TypeScript、ESLint、Prettier 和后端 Ruff 保证基础质量；后端用 Pytest 验证核心业务和异常分支；接口通过 OpenAPI/Swagger 或接口测试覆盖参数校验、鉴权和状态码；关键用户路径用 Playwright 做端到端测试，例如创建工作区、上传、等待处理、提问查看引用、删除数据。提交前做自测和代码评审，重点检查权限、异常处理、边界条件和可维护性。

> 发布时，小团队可以先在测试环境验证和小范围试用；有条件时采用灰度发布和可回滚版本。上线后关注前端错误、后端错误率、接口耗时、Worker 任务积压和失败率，并用日志中的 requestId 关联排查。

其中只保留项目实际已经具备的措施；没有做灰度或监控时，可以说“目前项目规模下还没有完整灰度体系，但如果投入生产，我会优先补充……”。

## 34. 如果重做一次，你会怎么改？

可以回答：

> 我会优先从可维护性、可靠性和检索质量三个方向改进。第一，进一步统一前后端 API 契约和错误码，减少联调歧义；第二，完善任务幂等、超时、重试和观测，避免 Worker 重复消费或任务长期卡住；第三，针对 RAG 建立更系统的评测集，持续衡量召回率、引用准确率和答案覆盖率。数据量增长后，我也会评估游标分页、向量索引策略和是否拆分专用检索服务。

> 我不会一开始就拆很多微服务。先根据真实瓶颈和用户量做度量，在现有清晰架构上迭代，避免无收益的复杂化。

## 35. 你怎么理解端到端 Ownership？

端到端 Ownership 是对用户最终拿到的结果负责，不只是完成一段代码。它包含确认需求和验收标准、设计数据与接口边界、推动开发和联调、验证正常与异常流程、上线后跟进问题。

以文档上传为例，责任不止是做一个按钮，还包括权限校验、上传成功后的任务状态、解析和向量化失败时的提示与重试、可检索时机、删除后的关联数据清理。这不要求一个人写完所有模块，但要求主动推动完整链路正确交付。
